# ADR-0009: Rendering hardware interface over Vulkan and Direct3D 12

- **Status:** Accepted
- **Amended by:** [ADR-0021](0021-rhi-device-structure-and-backend-modules.md)
- **Date:** 2026-11-20
- **Related:** [ADR-0001](0001-cpp-language-and-safety-rules.md) (no exceptions, no RTTI,
  `ith::Expected`), [ADR-0003](0003-clean-room.md), [ADR-0004](0004-modules-and-layering.md)
  (RHI in `platform`, no third-party types in public headers),
  [ADR-0005](0005-reference-hardware.md) (minimum GPU features, optional features per tier),
  [ADR-0007](0007-logging-and-profiling.md) (GPU zones),
  [ADR-0011](0011-shader-language-and-pipeline.md) (shaders)

## Context

Every renderer pass, the UI renderer and the editor viewport are written against the RHI, so its
shape is fixed before the first triangle. Vulkan and Direct3D 12 are both first-class on Windows;
Linux and Steam Deck use Vulkan. Consoles come later, in private repositories, as further
backends of the same interface.

ADR-0005 removes most of what makes an RHI large. Each API has exactly one binding model
(a global bindless heap) and one barrier model (Vulkan synchronization2, D3D12 enhanced
barriers), rendering is dynamic (no render-pass objects), and there are no legacy fallbacks.

Lessons from earlier engine prototypes by the same maintainer:

- An engine that exposed a third-party RHI's types in about 30 renderer headers could not add a
  backend without rewriting the renderer. Its Vulkan code also relied on catching Vulkan-Hpp
  exceptions, and it could not recreate or even cleanly report a lost device.
- An engine with its own handle-based, bindless RHI kept passes small and found that deferred
  destruction must wait not only for submitted work but also for command lists still being
  recorded. Debug names on every object and running the API validation layers in CI paid off.

Facts below were checked on 2026-11-20 against the projects' repositories and release tags, and
by compiling with Clang 19.1.5 using `-std=c++20 -fno-exceptions -fno-rtti -D_HAS_EXCEPTIONS=0`.

## Options considered

**A. NVRHI** (MIT, [repository](https://github.com/NVIDIA-RTX/NVRHI), commit `bf0bbd9`,
2026-10-28). A capable, actively developed RHI over D3D11, D3D12 and Vulkan 1.3 with bindless,
enhanced barriers, mesh shaders and ray tracing.
- Does not build under ADR-0001 without patches (verified): 12 errors in 5 files of the Vulkan
  backend (`try`/`catch (vk::DeviceLostError&)` on the wait-idle and submit paths, and call sites
  that assume Vulkan-Hpp's throwing return types); `checked_cast` uses `dynamic_cast` in a
  public header whenever `_DEBUG` is defined, so every MSVC Debug build fails; its validation
  layer needs RTTI. The device-lost path, which we must test, is the broken part.
- No releases or tags: we would maintain a patched fork of an untagged branch.
- Windows and Linux only; no console backends. A console port would implement its large virtual
  interface (well over a hundred methods) or bypass it.
- It would sit under `ith::rhi` as a second abstraction, with its own binding layouts and its own
  state tracker beside our render graph's barriers.
- Its CPU bookkeeping uses `new` and standard containers, so the engine allocator can't be
  plugged in.

**B. Diligent Engine** (Apache-2.0, last release v2.5.6, 2024-09-02). Exceptions are its error
model (`LOG_ERROR_AND_THROW` in 161 files of DiligentCore) with no build option to turn them off.
It is a full framework with its own shader tooling, far beyond an RHI, and its console backends
are not openly available.

**C. Our own thin RHI** over the APIs' C interfaces, with the vendors' GPU memory allocators.
- Fits ADR-0001 and ADR-0004 by construction: `ith::Expected` errors, our allocator, our handles.
- One interface for both desktop APIs and for future console backends.
- Cost: we write and maintain both backends. Earlier prototypes put this scope at roughly
  10–15k lines for two backends, written once, with no fork to track.

NVRHI remains a useful **design reference** for backend details: enhanced-barrier mapping, the
SM 6.6 root-signature flags, Vulkan feature-chain setup. We read it for ideas only and copy no
code, in the spirit of ADR-0003.

## Decision

### Structure

1. **Ironthorn has its own RHI**: `ith::rhi` (interface module) and the backend modules
   `rhi_vulkan` and `rhi_d3d12`, all in the `platform` layer. No backend or allocator type
   appears in any public header.
2. **Backends are chosen at start-up.** `rhi::Device` and `rhi::CommandList` are abstract
   classes with virtual functions; one backend is active per process. The default on Windows is
   Direct3D 12, and Vulkan can be selected by option. Linux, Steam Deck and Android use Vulkan.
   Bindless keeps the number of calls per draw low, so virtual dispatch cost is negligible.
3. **Dependencies, private to their backend:**

   | Library | Pin | License | Used by |
   |---|---|---|---|
   | [Vulkan-Headers](https://github.com/KhronosGroup/Vulkan-Headers) | `vulkan-sdk-1.4.363.0` | Apache-2.0 OR MIT | `rhi_vulkan` |
   | [Vulkan Memory Allocator](https://github.com/GPUOpen-LibrariesAndSDKs/VulkanMemoryAllocator) | v3.5.0 | MIT | `rhi_vulkan` |
   | [DirectX-Headers](https://github.com/microsoft/DirectX-Headers) | v1.620.2 | MIT | `rhi_d3d12` |
   | [D3D12 Memory Allocator](https://github.com/GPUOpen-LibrariesAndSDKs/D3D12MemoryAllocator) | v3.3.0 | MIT | `rhi_d3d12` |

   - Vulkan is used through its C API (`vulkan_core.h`); functions are loaded through
     `vkGetInstanceProcAddr` and `vkGetDeviceProcAddr` by the backend. Vulkan-Hpp is not used.
   - All four document and were verified to compile without exceptions and RTTI. Both allocators
     route CPU allocations to the engine allocator through their callbacks.
   - The Direct3D 12 **Agility SDK 1.620.2** (NuGet package `Microsoft.Direct3D.D3D12`, the
     retail line) ships with the game (ADR-0005). DirectX-Headers v1.620.2 states that it matches
     this package, and the two are always upgraded together. Preview Agility SDKs are not used.
     The Agility SDK's redistribution license is checked before the first release.
   - Each is pinned by URL and SHA-256 and added to `docs/development/third-party.md` together
     with the backend code that uses it.

### Resources and lifetime

4. **Typed generational handles** (`BufferHandle`, `TextureHandle`, `SamplerHandle`,
   `PipelineHandle`, …) refer to objects in device-owned pools. A stale handle is a detected
   error in Debug and development builds.
5. **Deferred destruction.** Destroying a handle queues the object until the GPU has finished
   every submission that could use it **and** every command list that was open at that moment
   has been submitted or discarded. Progress is tracked with a monotonically increasing value per
   queue (a Vulkan timeline semaphore, a D3D12 fence).
6. Every object takes a **debug name** at creation, passed to the API and to tools.

### Binding model

7. **One global bindless heap.** D3D12 uses one shader-visible CBV/SRV/UAV heap and one sampler
   heap, indexed in shaders through SM 6.6 `ResourceDescriptorHeap` and
   `SamplerDescriptorHeap`. Vulkan uses one descriptor set of runtime arrays (sampled images,
   storage images, storage buffers, samplers), partially bound and updated after bind.
8. **Shaders reach every resource, buffers included, by a bindless index** on both APIs, so a
   shader is written once. Buffer device addresses are not used for shader access. A resource
   keeps its index for its lifetime; an index is reused only after deferred destruction (rule 5).
9. **Per-draw and per-dispatch data travels in at most 128 bytes** of push constants (Vulkan) or
   root constants (D3D12). Larger data goes in a buffer whose index is in those constants.
10. **Capacities** are constants fixed at device creation and logged: 262,144 resource
    descriptors and 2,048 samplers (the D3D12 shader-visible sampler heap maximum). A device below
    them fails the start-up check with a named reason. The resource capacity can be raised when a
    tier needs it.

### Barriers

11. **Barriers are explicit.** The RHI does not track resource state. A barrier names the
    resource, the stages and accesses before and after, and the texture layout, which maps
    directly onto D3D12 enhanced barriers and Vulkan synchronization2. The render graph computes
    them; until it exists, passes declare them by hand.

### Commands, queues and frames

12. **Command lists** are recorded by one thread at a time and may be recorded in parallel. They
    come from per-frame, per-thread pools. Recording calls return nothing: misuse is caught by
    engine checks and the validation layers in Debug and development builds, and real failures
    surface at submit.
13. **Queues:** one graphics queue at first. Async compute and copy queues are added when the
    render graph schedules work for them and profiles show a gain.
14. **Frames in flight: two** (it may become a setting later). Per-frame resources are reused
    only after the GPU has finished that frame. `beginFrame` returns no frame when nothing should
    be drawn (a minimized window, a swapchain being recreated); the swapchain is recreated inside
    the backend.
15. **GPU profiling** (ADR-0007): a command list offers an engine-owned scoped GPU zone; the
    backends implement it with Tracy's Vulkan and D3D12 helpers in private sources.

### Shaders

16. **The RHI takes compiled shaders**: SPIR-V for Vulkan, DXIL for D3D12, each with the
    reflection data the pipeline needs (entry points, stage, constant size). Both come from the
    Slang pipeline of ADR-0011. The RHI rejects a shader whose constants exceed rule 9 or that
    declares resources outside the bindless model.

### Features and tiers

17. **Start-up capability check.** The device is created only if it meets the ADR-0005 minimum,
    and every missing feature is reported by name. Optional features (mesh shaders, hardware ray
    tracing, variable-rate shading, sampler feedback) are reported in a capabilities struct and
    enabled per scalability tier. Calling an optional feature's commands on a device without it
    is an assert. No feature needed at the Low tier may depend on an optional capability.

### Validation and errors

18. **Validation** uses the API debug layers: the D3D12 debug layer (GPU-based validation on
    request) and the Vulkan validation layers including synchronization validation. They are on
    by default in Debug, switchable in development builds and never present in shipping builds.
    CI runs the functional GPU tests on WARP and lavapipe with validation on (ADR-0005).
19. **Errors without exceptions.** Creation calls return `ith::Expected<Handle, rhi::Error>`.
    Device loss and out-of-memory are returned from submit and present as `rhi::Error`. On
    device loss the engine logs the API's diagnostics (DRED on D3D12, `VK_EXT_device_fault`
    where available), writes a crash report and shuts down through the fatal path. This is the
    P1 behaviour; recreating the device without a restart is later work.

## Consequences

- Renderer code is written once against a small interface, and console backends implement that
  same interface in private repositories.
- No exception or RTTI concessions, no fork to maintain, and four new pinned dependencies, all
  MIT or dual-licensed from the API vendors.
- We own two backends, their bugs and their driver workarounds. Bindless bugs (a stale or
  out-of-range index) are harder to see, which debug names, handle checks and GPU-based
  validation offset.
- Explicit barriers make the render graph responsible for correctness; synchronization
  validation in CI is the safety net.
- Follow-up work: the shader pipeline ADR (ADR-0011); `rhi`, `rhi_vulkan` and `rhi_d3d12` with
  a triangle, then 10k instanced meshes on both backends; a device-loss test; the Agility SDK
  redistribution license check.
- **Revisit when:**
  - a target device fails the capacities of rule 10, or descriptor updates show up in profiles
    (consider `VK_EXT_descriptor_buffer`);
  - shipping requires recovering from device loss without a restart;
  - a console target is chosen;
  - a needed Direct3D 12 feature exists only in a preview Agility SDK;
  - the schedule cannot carry two backends, in which case a patched, forked NVRHI behind the same
    interface is the fallback, recorded in a new ADR.
