## Context

Reflection is the engine's description of its data types. The ECS, serialization, the Details
panel, Play In Editor's world copy, replication, save games, hot reload and visual scripting all
read it, and ADR-0014 needs its core before ECS slice 2. It must:

- work without RTTI and exceptions;
- give **stable type ids**, identical on every compiler and platform and surviving renames;
- describe each type for type-erased code: size, alignment, construct, copy, move, destroy, and
  each field's offset and type;
- carry attributes: ranges, units, categories, tooltips and flags (`EditorOnly`, `Transient`,
  `Replicated`, `SaveGame`);
- be declared once, next to the type, with no hand-written tables.

Lessons from earlier engine prototypes by the same maintainer:

- Hand-written builder tables with `std::function` getters and setters worked for a few types
  but stayed thin: no nested lists of structs, no categories, no registry. Each new consumer
  needed it extended, and the tables drifted from the types.
- Validating a whole edit before applying any of it (parse, then apply, which can't fail) was
  worth keeping, and so were descriptions and ranges per field.
- An earlier design required metadata to be plain data, not language tricks, so other languages
  and tools could read it later.

Facts below were checked on 2026-11-20.

## Options considered

**A. A generator on libclang** (LLVM
[23.1.6](https://github.com/llvm/llvm-project/releases/tag/llvmorg-23.1.6), 2026-11-17,
Apache-2.0 WITH LLVM-exception). Parses real C++, so any syntax works, and annotations can be
Clang attributes. Costs:
- every build needs it, players and shipping CI included, because the player needs the
  generated code: the prebuilt archives are about 263 MiB (Windows, `.tar.zst`) and 1.1 GiB
  (Linux, `.tar.zst`); the separate Python wheel is stuck at 18.1.1 (2024);
- each header is parsed with its full include closure and the module's compile flags, which
  costs seconds per header without a cache;
- one more pinned toolchain to upgrade. That the archives contain libclang for both hosts in
  the needed form wasn't verified.

**B. Our own annotation scanner** over a restricted header syntax. A small C++ tool built from
source with the engine, no dependency, milliseconds per header. It only finds annotated
declarations and copies names and attributes. **It doesn't need to understand C++ types:** the
generated code is compiled by the real compiler, which works out sizes, offsets and field types
(`sizeof`, `offsetof`, `decltype`), so a scanner mistake becomes a compile error, not wrong
data. Unusual syntax is refused with a clear error rather than parsed. Unreal's header tool is,
by its public documentation, also a purpose-built parser of annotated headers rather than a
compiler front end.

**C. No generator: macros or `constexpr` registration in the type.** No tool, but every field
is named twice, which is the hand-written table again and drifts the same way.

**D. C++26 static reflection.** The right long-term answer, but C++26 isn't the engine
standard (ADR-0001). GCC 16 reportedly ships it behind `-freflection` (not checked against
GCC's release notes); upstream Clang (the reference compiler) and MSVC don't
([clang-p2996](https://github.com/bloomberg/clang-p2996) is an experimental fork). Rejected
for now.

**E. A third-party runtime reflection library** (RTTR, `entt::meta`, flecs meta). Each brings
its own registry and value types, none gives stable cross-compiler ids, and most still need
hand registration. Rejected.

## Decision

### Generator

1. **Reflection is generated by our own scanner** (option B), `ith_reflect`, a standard-library
   C++ build tool in `tools/`. It is not an engine module and links into nothing; it is built for
   the host in every configuration, with or without `IRONTHORN_BUILD_TOOLS`. It needs no
   third-party dependency.
2. **Build integration.** `ith_add_module` runs it over the module's headers and writes one
   `generated/<module>/<module>.reflect.cpp`, compiled into the module, holding the type
   records and the module's registration function (ADR-0017 rule 5). It reruns only when a
   header of the module changes, and rewrites the file only when its content changes. The
   module's kind is passed in, so `EditorOnly` outside an `editor` module is a generation error.
3. **Restricted syntax.** An annotated type is `struct`, `class` or `enum class` at namespace
   scope, written on its own lines; a reflected field is one declarator per line. Annotations
   inside `#if` blocks, nested types and templates are refused with `file:line` errors. The
   scanner tracks namespaces, braces, comments and strings, nothing more.

### Annotations

4. Our own macros; they expand to nothing for the compiler except a friend declaration:

   ```cpp
   namespace game {
   struct Health {
       ITH_TYPE(Component, Category = "Combat")
       ITH_FIELD(Min = 0, Max = 10000, Tooltip = "Hit points", Replicated, SaveGame)
       float current = 100.0f;
       ITH_FIELD(Min = 1, Max = 10000)
       float maximum = 100.0f;
       float cachedRatio = 1.0f;   // not reflected
   };
   enum class ITH_ENUM() DamageKind : std::uint8_t { Physical, Fire, Poison };
   }
   ```
   - `ITH_TYPE` takes a role (`Struct`, `Component`, `Resource`, `Event`, `Asset`) and attributes;
     `ITH_ENUM` covers plain and flag enums. **Fields are opt-in** with `ITH_FIELD`.
   - Attributes: flags `EditorOnly`, `Transient`, `ReadOnly`, `Replicated`, `SaveGame`; values
     `Min`, `Max`, `Unit`, `Category`, `DisplayName`, `Tooltip`, `FormerName`; free key-value
     strings in `Meta(...)` for plugins. An unknown attribute is a generation error.
5. **What is reflected now:** structs, components, resources, events, enums and their fields.
   Field types are primitives, strings, `Uuid`, handles, asset references, gameplay tags, math
   types (ADR-0006), enums, nested reflected structs, fixed arrays, `std::optional` and
   dynamic arrays. Leaf types are described once by hand-written traits in `core/reflection`;
   those few are the only hand-written descriptions. No inheritance between reflected types;
   composition only. **Functions** come with the visual scripting ADR (P5) as `ITH_FUNCTION`.
6. **Reflected structs are standard-layout** (a generated `static_assert`), so `offsetof` is
   well defined and type-erased copies are safe.

### Identity

7. **A type id is the 64-bit FNV-1a hash** (`ith::fnv1a64`) of the fully qualified name as
   written (`game::Health`), computed by the generator, so it is identical on every compiler.
   Field ids are the hash of the field name. The function is fixed: ids appear in cooked data.
8. **Renames keep data.** `FormerName = "game::Hp"` on a type or field registers the old
   name and id as aliases: source files that use the old name load, and are saved with the new
   one (ADR-0010). Cooked data is recooked. A collision of two ids in one process is a fatal
   startup error naming both types.

### Runtime

9. **`core/reflection`** (layer `core`, kind `runtime`) holds the registry and records:
   - `TypeInfo`: id, name, role, size, alignment, function pointers for default construct,
     copy, move, destroy and field-wise equality (over reflected fields), flags, attributes,
     and its fields or enumerators;
     ADR-0014's component type records are these;
   - `FieldInfo`: id, name, offset, its `TypeInfo`, flags and attributes; containers add
     element access through a small function table;
   - `ith::typeOf<T>()` (a compile error for an unreflected `T`), `TypeRegistry::find(id)` and
     `find(name)` (aliases included), returning a pointer that is null when not found.

   Records are static data from the generated files; lookups don't allocate. The registry is
   filled by the registration functions at startup and is read-only afterwards. Hot reload
   (ADR-0016 rule 19) re-registers a module; its ADR defines how.
10. **Edits are validated, then applied** (the lesson above): reading data into an object builds
    and checks a patch first, and applying it can't fail.

### Configurations

11. **Shipping keeps** names, ids, layout, flags and `Min`/`Max` (loading and replication use
    them) and **compiles out** human-facing text: `Tooltip`, `Category`, `DisplayName` and
    `Meta` (empty in Shipping). Every target of a configuration gets the same records
    (ADR-0017 rule 3).

### Tests

12. - Scanner tests on fixture headers, including every refused construct and its message, and
      golden files of the generated output.
    - **Round-trip of every reflected type**, the P1 exit criterion: a test walks the registry,
      fills each type with deterministic non-default values, writes and reads it through the
      text and binary archives (ADR-0010) and compares with the type's equality. It runs under
      the sanitizer jobs, which also exercise construct, copy, move and destroy.
    - Registry tests: unique ids, aliases, collisions, unknown names.

## Consequences

- Types are declared once; every consumer reads the same records, with no RTTI and no
  dependency.
- Header authors live with a restricted syntax for reflected types; the scanner's errors must
  be clear, and its test suite grows with every refused construct.
- Opt-in fields mean a forgotten `ITH_FIELD` silently doesn't save or replicate; the Details
  panel showing every reflected field makes this visible early.
- Reflected structs must be standard-layout, which keeps components plain data (ADR-0016).
- Follow-up work: `ith_reflect` with tests; `core/reflection` with leaf traits; the generator
  step in `ith_add_module`; the round-trip test; then ECS slice 2.
- **Revisit when:**
  - the scanner's restrictions block real code often (move to libclang behind the same output);
  - Clang, MSVC and console toolchains all ship C++26 reflection (generate less, or nothing);
  - a console cross-build can't run a host tool in the same CMake build;
  - other languages need the metadata (export it as data with the C ABI).
